## 1. Executive Summary

In enterprise environments, AI agents execute critical business tasks by calling APIs, modifying databases, and triggering side-effecting financial transactions. Testing whether the final sentence generated by an LLM "sounds good" is insufficient: an agent can produce polite, reassuring text while violating critical operational invariants (such as refunding an order before checking if the order is eligible).

This project demonstrates how to solve this using `aireliability`:
- Capture runtime tool calls into a typed, standardized **`ExecutionTrace`**.
- Validate trajectories against deterministic operational invariants with **`ToolOrder`**.
- Catch invariant violations and produce structured, actionable **`FailureReport`** objects using **`FailureAnalyzer`**.
- Automatically turn production or staging failures into permanent regression suites with **`RegressionGenerator`**.

## 2. Why Traditional Testing Fails for AI Agents

| Dimension | Standard Unit Testing | LLM-as-a-Judge Evaluation | Invariant Testing (`aireliability`) |
| :--- | :--- | :--- | :--- |
| **Target** | Deterministic function `f(x) == y` | Final generated natural language text | Intermediate tool execution trajectory |
| **Observation** | Return values only | Surface semantics & grammar | Side-effects, tool arguments, tool order |
| **Determinism** | 100% deterministic | Non-deterministic & stochastic | 100% deterministic mathematical evaluation |
| **Speed & Cost** | Instant, $0 cost | High latency, token costs | Instant, $0 cost, zero network calls |
| **Catches Order Bugs** | No (agent is dynamic) | Often misses tool-order side-effects | **Yes (Guaranteed by subsequence/exact assertions)** |

## 3. The Business Scenario & The Problem

### Scenario: Customer Refund Agent
A customer support agent receives the request:
> *"Refund order ORD-1001"*

### The Business Rule / Invariant:
```text
check_order  ──▶  refund_order
```
The agent **MUST** call `check_order(order_id)` before calling `refund_order(order_id)`.

### The Deceptive Problem:
Both the correct agent and a broken agent output the exact same final text:
> `"Order ORD-1001 refunded successfully"`

- **Correct Agent**: Checks eligibility $\rightarrow$ Issues refund. (Passes invariant)
- **Broken Agent**: Issues refund $\rightarrow$ Checks eligibility. (**Violates invariant**, resulting in unauthorized financial disbursement!)

A traditional test asserting `assert "refunded successfully" in response` passes for both agents! Only trajectory-level reliability testing catches the broken agent.

## 6. Detailed Code Walkthrough: What We Built

### Part 1: The Agent & Execution Traces (`app.py`)

In [`app.py`](file:///Users/livesh/Ai_reliabilty%20test/aireliability-mini-demo/app.py), we implemented two tools and two agent implementations:

1. **Tools**:
   - `check_order(order_id)`: Simulates eligibility lookup returning `{"order_id": order_id, "eligible": True}`.
   - `refund_order(order_id)`: Simulates refund transaction returning `{"order_id": order_id, "status": "refunded"}`.

2. **`refund_agent(order_id)` (Correct)**:
   - Calls `check_order` first, records a `TraceStep(type=StepType.TOOL, name="check_order", ...)`.
   - Calls `refund_order` second, records a `TraceStep(type=StepType.TOOL, name="refund_order", ...)`.
   - Packages the steps into an `ExecutionTrace` with `trace_id`, timestamps, user request, and final output.

3. **`broken_refund_agent(order_id)` (Intentional Regression)**:
   - Inverts the sequence: calls `refund_order` before `check_order`.
   - Still returns `"Order ORD-1001 refunded successfully"` (demonstrating how dangerous silent regressions are).

```python
# app.py snippet
def refund_agent(order_id: str) -> tuple[str, ExecutionTrace]:
    t_start = datetime.now(timezone.utc)
    steps: list[TraceStep] = []

    chk_res = check_order(order_id)
    steps.append(TraceStep(type=StepType.TOOL, name="check_order", input={"order_id": order_id}, output=chk_res))

    ref_res = refund_order(order_id)
    steps.append(TraceStep(type=StepType.TOOL, name="refund_order", input={"order_id": order_id}, output=ref_res))

    t_end = datetime.now(timezone.utc)
    final_output = f"Order {order_id} refunded successfully"

    trace = ExecutionTrace(
        trace_id=f"trace_{uuid.uuid4().hex[:12]}",
        test_id="refund_order_flow",
        started_at=t_start,
        completed_at=t_end,
        input={"request": f"Refund order {order_id}"},
        output=final_output,
        steps=steps,
    )
    return final_output, trace
```

### Part 2: Invariant Evaluation & Regression Synthesis (`reliability_test.py`)

In [`reliability_test.py`](file:///Users/livesh/Ai_reliabilty%20test/aireliability-mini-demo/reliability_test.py), we verify agent executions and handle failures:

1. **Define the Invariant**:
   ```python
   invariant = ToolOrder(expected_order=["check_order", "refund_order"])
   ```
2. **Evaluate Correct Agent**:
   - `invariant.evaluate(correct_trace, test_case)` returns `EvaluationResult(passed=True)`.
3. **Evaluate Broken Agent**:
   - `invariant.evaluate(broken_trace, test_case)` returns `EvaluationResult(passed=False)`.
4. **Structured Failure Analysis**:
   ```python
   analyzer = FailureAnalyzer()
   report = analyzer.analyze(broken_trace, eval_fail, test_id=test_case.id)
   ```
   Extracts `failure_id`, taxonomy `category`, `severity`, descriptive `message`, and exact `evidence` diff.
5. **Automated Regression Generation**:
   ```python
   generator = RegressionGenerator()
   reg_test = generator.generate(report, test_case)
   ```
   Creates a reproducible `RegressionTest` object permanently linked to `source_failure_id`.

## 8. Under the Hood: How `aireliability` Works Internally

1. **Step Filtering**:
   When `ToolOrder.evaluate(trace)` is invoked, it extracts all steps where `step.type == StepType.TOOL`:
   ```python
   tool_names = [step.name for step in trace.steps if step.type == StepType.TOOL]
   ```
2. **Subsequence Matching Algorithm**:
   It uses Python iterator chaining to test if `expected_order` exists as an ordered subsequence:
   ```python
   it = iter(tool_names)
   passed = all(tool in it for tool in self.expected_order)
   ```
   This ensures that other non-conflicting tools (e.g. `audit_log`, `notify_user`) can run without causing brittle test failures, while strictly enforcing order precedence.
3. **Structured Taxonomy & Evidence**:
   `FailureAnalyzer` populates the `evidence` dictionary containing both `expected_order` and `actual_order`, formatting the exact mismatch so developers can instantly locate the offending prompt or tool call.
4. **Traceability**:
   Every generated regression test preserves `source_failure_id`, connecting future CI test assertions directly back to the historical production incident or trace.

## 10. 10 Likely Interview Questions & Concise Answers

1. **Q: Why can't traditional unit tests solve this problem?**
   **A:** Traditional unit tests verify deterministic return values of static functions. AI agents dynamically choose tool sequences, so testing only the final string output misses unauthorized or inverted tool executions.
2. **Q: What is an `ExecutionTrace`?**
   **A:** An `ExecutionTrace` is a standardized schema that records an agent's full runtime trajectory: inputs, final outputs, timestamps, and intermediate `TraceStep` tool calls.
3. **Q: Why use deterministic assertions like `ToolOrder` instead of LLM-as-a-judge?**
   **A:** Deterministic assertions run in microseconds, cost $0, require no network calls, and are 100% reproducible. LLM judges are slow, expensive, and can hallucinate false passes.
4. **Q: Does `ToolOrder` allow intermediate tools between `check_order` and `refund_order`?**
   **A:** Yes. By default, `ToolOrder` validates subsequences, allowing intermediary actions (like logging or telemetry). You can also enforce `exact_match=True` if no intermediate tools are permitted.
5. **Q: What does `FailureAnalyzer` do?**
   **A:** It maps evaluation mismatches into structured `FailureReport` objects containing failure taxonomy (`category`, `type`), severity ratings, and before/after diff evidence.
6. **Q: What is the purpose of `RegressionGenerator`?**
   **A:** It turns transient failures into persistent, reproducible `RegressionTest` definitions that link back to the originating `source_failure_id`, automating regression test authoring.
7. **Q: How does this package avoid external dependencies?**
   **A:** It is architected around pure data contracts and mathematical evaluation logic implemented with Pydantic and standard Python libraries.
8. **Q: How would you capture traces in a production agent using LangChain or OpenAI?**
   **A:** By instrumenting tool callbacks or response handlers that instantiate a `TraceStep(type=StepType.TOOL)` for each tool call and appending them to the active `ExecutionTrace`.
9. **Q: What happens if an agent fails to call a tool entirely?**
   **A:** `aireliability` provides expectations like `ToolCalled(tool_name)` and `ToolNotCalled(tool_name)` to enforce presence or absence of specific actions.
10. **Q: How does this fit into a CI/CD pipeline?**
    **A:** The regression suite is stored as test definitions. When developers update system prompts or switch model versions, CI re-runs these test cases to verify no business invariants are broken.

## 11. What We Learned & Next Steps for Real LLMs

### Key Takeaways
1. **Trajectories Matter More Than Text**: In tool-calling agents, intermediate side-effects define business reliability, not surface-level natural language fluency.
2. **Determinism Provides True Safety**: Operational invariants should be verified deterministically rather than delegating safety checks to probabilistic LLM evaluators.
3. **Closing the Loop (Failure $\rightarrow$ Regression)**: Converting production trace failures directly into regression tests creates a self-healing quality pipeline.

### Extending to Real LLM Agents
To connect this architecture to a live LLM (such as GPT-4o, Claude 3.5, or Gemini):
1. **Interception**: Add a decorator or callback around the model's tool execution dispatcher.
2. **Telemetry Ingestion**: Every time the LLM outputs a tool call (e.g. `tool_calls=[{"name": "check_order", "args": {...}}]`), instantiate a `TraceStep(type=StepType.TOOL, ...)`.
3. **Continuous Evaluation**: Feed the resulting `ExecutionTrace` into `ToolOrder.evaluate()` and publish metrics to observability backends.
